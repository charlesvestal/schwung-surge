# The Remote UI

`src/remote/web_ui.html` is the Surge XT module's browser instrument. Schwung
Manager finds a `web_ui.html` beside `module.json` and, when the module is in a
shadow slot, shows it in a sandboxed iframe on `http://move.local:7700/remote-ui`
in place of the knob view it would otherwise generate. It is built for an iPad
in landscape first -- everything is a touch surface -- and for a Mac browser and
the Manager's pop-out window after that.

## What it is

Surge has no front panel to be faithful to; its identity is depth. So the page
is direct manipulation wherever a picture can stand in for a knob, and the
pictures are Surge's own, not drawings of what Surge might do:

- **Oscillators** show the waveform Surge actually produces, rendered by the
  plugin exactly as Surge's own oscillator display renders it (`spawn_osc`, a
  block loop through the half-rate filter). Type is a strip of tiles.
- **Filters** are an XY pad -- cutoff across, resonance up -- with both filters'
  measured magnitude responses drawn behind the nodes, measured by the plugin
  the way Surge's Filter Analysis measures them (a log sweep through the real
  filter unit). Both scenes, both filters.
- **Envelopes** are graphs whose corners you drag.
- **LFOs** run at their rate; **modulation** is six slots you set plus every
  routing the patch holds, and each knob shows how far modulation can move it.
- **Macros** are eight big faders labelled by the patch. **FX** are all sixteen
  slots. **Scene B** is the same page with a cold colour. **Presets** are 675
  tiles under a category rail with search and favourites.
- **Values read as Surge reads them** -- Hz, seconds, dB, semitones, note names,
  tempo-synced note lengths -- because the page ports `Parameter::get_display`
  and is fed each parameter's own display description.

**Every control sits in the same cell.** A cell is a two-line label, a control
box of fixed height and a one-line value, and a section's controls are laid in a
grid of equal columns: knobs in one row therefore sit exactly under knobs in the
next whatever their labels wrap to, switches and menus share the row's baseline,
and a menu takes two columns, a segmented strip three (two when it has two
options). A segmented strip is only offered when its words are short enough to
sit side by side; otherwise the same parameter is a menu that opens a searchable
sheet. Macros are eight wide horizontal faders, one per row, label left and value
right, so nothing ever sits over a word. In the FX tab the sixteen slots are four
uniform cards per row -- name and type -- and each ACTIVE slot gets a full-width
strip under its row with its twelve controls in a line. (The first cut had
flex-wrapped cells of different widths and vertical macro faders whose thumbs
covered their labels; on the iPad the controls did not line up and the
modulation slots overlapped. That is the layout this replaced.)

Touch: 44 px minimum targets; drags are relative and never jump; a value bubble
sits above the finger; a second finger held anywhere (or the Fine switch) turns
any drag fine; double-tap resets to Surge's default; long-press types a value.
Everything is also keyboard-operable. Two designed themes, dark and light.

## What the plugin does for the page

The page sees the module only through Schwung Manager, which hands a browser
two things, both from inside the host's 64 KB parameter buffer: our `state`
blob flattened one field per key, and `chain_params`. **`chain_params` with
Scene A alone is already 60.8 KB**, so it is untouched and carries nothing new.
Everything else is files, written by a worker thread in the plugin to
`<module_dir>/remote/` and served by the manager's module-assets route:

- **`state`** now carries every registered parameter -- Scene A with its
  historical bare keys (`osc1_pitch`), Scene B with Surge's `b_` prefix, global
  with `g_` (`g_volume`, `g_scenemode`, `g_splitkey`, and the four send
  returns `g_volume_FX1..4`), the sixteen FX slots as `fx<slot>_type` /
  `fx<slot>_p<n>` where `<slot>` is Surge's ZERO-based slot index (A1-A4 are
  0-3, B1-B4 4-7, sends 8-11, global 12-15; Surge's own storage names are
  one-based, `fx1_p0`) -- plus the eight macros (`macro1`..`macro8`, 0..1).
  765 parameters, about 17 KB. Save and restore are therefore complete for the
  first time; old states still restore, because Scene A keys and the registry
  ORDER (which mod-slot destinations index) are unchanged. Surge's global
  `fx_disable` bitmask (`ct_none`, range INT_MIN..INT_MAX) is deliberately not
  registered: it is not a control, and walking that range as options is what
  crashed the first build.
- **`patch_params.json`**: every parameter's key, full and short name, scene,
  control group, control type, value type, range, default, bipolarity, extend /
  tempo-sync / absolute / deactivate flags and states, and Surge's `displayInfo`
  verbatim; every option text for integer parameters; a 65-point table of
  Surge's own text for the few float types it formats by hand; five reference
  strings (`chk`) for every other float; the macro labels, the wavetable names,
  and the patch's modulation routings with their depths. Rewritten after every
  preset load and after any type change (oscillator, filter, waveshaper, LFO,
  FX types rename and retype their dependants -- and Surge applies the switch on
  the audio thread, so the registry is re-populated on the worker a beat later).
- **`presets_index.json`**: the patch list in display order, grouped by category
  with a factory / third-party / user kind. **`waves.json`**: 512 points per
  oscillator, both scenes. **`filters.json`**: 96 log-spaced dB values per
  filter unit, both scenes, plus the frequency axis.

Requests from the host thread only set bits and poke a condition variable; the
worker coalesces a burst (a knob drag is dozens) into one write ~150 ms later,
writes to a temp name and renames. Each file carries a `rev`. The worker lives
inside Move's process, so every writer runs under `try`/`catch` and
`patch_params.json` is formatted from a snapshot of the registry taken under the
lock, not with the lock held: the host's parameter thread takes that lock for
every `find_param`.

**Writes** go through `schwungRemote.setParam` in the units the plugin's
`set_param` already took: Surge's natural value for floats and plain ints, the
option TEXT for enumerated ints, 0..1 for macros, `On`/`Off`, a source name and
a destination KEY for mod slots. A preset is `preset` = display index; the
manager then re-reads the whole state itself, and the page re-reads
`patch_params.json` until it names the preset the state names.

## Verifying the port

`node tests/remote/format_test.mjs tests/remote/fixtures/patch_params.json`
formats every float parameter at 0, 25, 50, 75 and 100 % with the page's port
and compares against the five strings Surge wrote into `chk`. A disagreement is
a bug in the port, never accepted as "close enough". Capture a fixture from a
running module with the manager's asset route:
`curl -o tests/remote/fixtures/patch_params.json http://move.local:7700/api/remote-ui/module-assets/surge/remote/patch_params.json`.

## Testing the plugin without the Move UI

The Move has `gdb`, `gdbserver` and `strace`. The JE-8086 repo's
`plugin_host_test` (built for ARM with its Docker image) dlopens a `dsp.so`, calls
`create_instance` with a module dir and renders; against a copy of the module
under `/data/UserData/jp8000_test/surge/` (dsp.so, module.json, `surge-data`
symlinked to the real one) it reproduces a load-time crash in seconds, and
`gdb -q -batch -ex run -ex bt --args ./plugin_host_test ./surge/dsp.so ./surge 4`
names the frame. It also writes `remote/*.json` into that dir, which is where the
fixtures in `tests/remote/fixtures/` come from. The harness reports "boot timeout"
because Surge has no `__status` key; that is not a failure.

## Traps carried over from the JE-8086 page

- A canvas is never a grid item: its intrinsic size is its backing store, and
  on a Retina screen that inflates an auto track on every redraw. Every canvas
  here is absolute inside a box that owns the size.
- Never `schwungRemote.resubscribe()` from a slot page: the manager answers
  with a hierarchy message and its page re-renders the slot, iframe included.
- Preset loads land in stages; confirm by content, not by the first re-read.
